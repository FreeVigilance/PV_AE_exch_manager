# Reccon — система для проведения сверок данных по безопасности лекарственных препаратов

<div align="center">

**Веб-система для обмена служебными сообщениями между компаниями, подтверждения получения сообщений и проведения сверок по статусам за выбранный период**

</div>

## Обзор проекта

**Reccon** — это full-stack веб-приложение, разработанное для автоматизации обмена служебными сообщениями между компаниями и контроля факта их просмотра и подтверждения.

Система позволяет отправлять сообщения между организациями, прикреплять вложения, отслеживать статусы сообщений, фиксировать подтверждения, проводить сверки за выбранный период, работать с этапами сверки, обсуждать уточнения в чате и экспортировать результаты в формате XLSX.

Проект реализован как учебная система, приближенная к прикладному сценарию в области фармаконадзора, где важно контролировать факт обмена данными между компаниями и сохранять историю действий пользователей.

## Основные возможности

- Авторизация пользователей и разграничение доступа по компаниям.
- Работа с входящими, исходящими сообщениями и черновиками.
- Создание, редактирование, сохранение и отправка сообщений.
- Подтверждение входящих сообщений с указанием входящего номера.
- Поддержка статусов сообщений:
  - `черновик`;
  - `ожидает подтверждения`;
  - `прочитано`;
  - `подтверждено`.
- Прикрепление вложений к сообщениям и скачивание файлов.
- Создание сверок между компаниями за выбранный период.
- Работа с этапами сверки и сохранение snapshot-данных.
- Чат внутри сверки.
- Экспорт результатов сверки в XLSX.
- Внутренние уведомления о неподтвержденных сообщениях.
- Email-напоминания через отдельный worker-процесс.
- Административный раздел для управления пользователями, компаниями и настройками напоминаний.
- Swagger/OpenAPI-документация backend API.
- Контроль доступа к данным только в пределах компании пользователя.

## Жизненный цикл сообщения

Сообщение в системе проходит несколько основных этапов:

```text
черновик → ожидает подтверждения → прочитано → подтверждено
```

1. Пользователь создает сообщение и может сохранить его как черновик.
2. После отправки сообщение получает статус `ожидает подтверждения`.
3. Когда получатель открывает входящее сообщение, система фиксирует просмотр и переводит сообщение в статус `прочитано`.
4. После подтверждения с указанием входящего номера сообщение получает статус `подтверждено`.
5. Неподтвержденными считаются сообщения в статусах `ожидает подтверждения` и `прочитано`.

## Сверки и этапы

Сверка создается между двумя компаниями за выбранный период. В нее включаются сообщения, относящиеся к выбранному контрагенту и периоду.

На детальной странице сверки отображаются:

- компания-контрагент;
- период сверки;
- текущий этап;
- общее количество сообщений;
- количество подтвержденных сообщений;
- количество сообщений, ожидающих подтверждения;
- таблица сообщений;
- чат сверки;
- действия для создания нового этапа, завершения сверки и экспорта.

### Этапы сверки

Каждая сверка состоит из этапов. При создании нового этапа предыдущий этап сохраняется как snapshot и не изменяется задним числом.

Это позволяет видеть состояние сверки на момент формирования каждого этапа, даже если после этого сообщения были подтверждены или изменили статус.

### Экспорт

Результаты сверки можно выгрузить в XLSX:

- экспорт текущего этапа;
- экспорт всех этапов сверки;

## Архитектура

Проект состоит из клиентской части, серверной части, базы данных, объектного хранилища и фонового worker-процесса.

```text
Пользователь
    ↓
React Frontend
    ↓ REST API
Django REST Framework Backend
    ↓
PostgreSQL + MinIO / S3-compatible storage
    ↓
Worker для напоминаний
```

### Основные компоненты

- **Frontend** отвечает за пользовательский интерфейс, формы, таблицы, карточки, статусы, модальные окна и взаимодействие с API.
- **Backend** реализует бизнес-логику, REST API, авторизацию, проверку прав доступа, работу с сообщениями, сверками, вложениями, уведомлениями и экспортом.
- **PostgreSQL** используется для хранения пользователей, компаний, сообщений, сверок, этапов, чата, уведомлений и журнала действий.
- **MinIO / S3-compatible storage** используется для хранения вложений.
- **Worker** обрабатывает напоминания и отправку email-уведомлений.

## API и Swagger

Backend предоставляет REST API для взаимодействия с frontend-приложением. Для просмотра и проверки API используется Swagger/OpenAPI.

Основные группы endpoint-ов:

```text
/api/auth/                 # авторизация, refresh, текущий пользователь, выход
/api/messages/             # сообщения, входящие, исходящие, черновики, подтверждение
/api/attachments/          # загрузка и скачивание вложений
/api/reconciliations/      # сверки, этапы, чат, экспорт XLSX
/api/notifications/        # уведомления и счетчики неподтвержденных сообщений
/api/admin/                # пользователи, компании, настройки напоминаний
/api/audit/                # журнал значимых действий пользователей  
/api/docs/                 # Swagger/OpenAPI документация
```

Swagger позволяет проверить доступные методы, параметры запросов, структуру ответов и основные сценарии работы API.

## Локальный запуск

### Backend

Перейдите в папку backend:

```bash
cd reccon-system-backend/backend
```

Создайте и активируйте виртуальное окружение:

```bash
python -m venv .venv
source .venv/bin/activate
```

Для Windows:

```bash
.venv\Scripts\activate
```

Установите зависимости:

```bash
pip install -r requirements.txt
```

Примените миграции:

```bash
python manage.py migrate
```

Запустите сервер разработки:

```bash
python manage.py runserver
```

Backend будет доступен по адресу:

```text
http://localhost:8000
```

Swagger-документация:

```text
http://localhost:8000/api/docs/
```

---

### Frontend

Перейдите в папку frontend:

```bash
cd reccon-frontend
```

Установите зависимости:

```bash
npm install
```

Запустите frontend в режиме разработки:

```bash
npm run dev
```

Frontend будет доступен по адресу, который выведет Vite, обычно:

```text
http://localhost:5173
```

---

### Docker Compose

Для локального запуска инфраструктурных сервисов можно использовать Docker Compose:

```bash
docker compose up --build
```

Docker Compose может использоваться для запуска базы данных, объектного хранилища и вспомогательных сервисов, необходимых для локальной разработки.

## Основные пользовательские сценарии

### 1. Создание и отправка сообщения

1. Пользователь входит в систему.
2. Открывает форму создания сообщения.
3. Выбирает компанию-получателя.
4. Указывает тему и текст сообщения.
5. При необходимости прикрепляет файл.
6. Сохраняет сообщение как черновик или отправляет его.
7. После отправки сообщение появляется у получателя во входящих.

### 2. Подтверждение входящего сообщения

1. Пользователь компании-получателя открывает список входящих сообщений.
2. Открывает карточку сообщения.
3. Система фиксирует просмотр сообщения.
4. Пользователь указывает входящий номер.
5. Подтверждает получение сообщения.
6. Система переводит сообщение в статус `подтверждено`.

### 3. Работа со сверкой

1. Пользователь компании-получателя создает сверку с выбранной компанией-контрагентом и периодом.
2. Система формирует первый этап сверки и включает в него сообщения, относящиеся к выбранному периоду и контрагенту.
3. На детальной странице сверки отображаются сводные показатели, таблица сообщений, текущий этап, фильтрация и чат.
4. Пользователь компании-отправителя просматривает сообщения в сверке и подтверждает сообщения, как факт того, что все было проверено.
5. После подтверждения сообщений со стороны компании-отправителя пользователь компании-получателя может создать новый этап сверки либо завершить её.
6. При создании нового этапа предыдущий этап сохраняется как snapshot и больше не изменяется задним числом.
7. Пользователи компаний могут обсуждать уточнения в чате внутри сверки.
8. После завершения или в процессе работы со сверкой пользователь может экспортировать результаты.

### 4. Экспорт результатов

1. Пользователь открывает детальную страницу сверки.
2. Нажимает кнопку экспорта.
3. Выбирает экспорт текущего этапа или всей сверки.
4. Система формирует XLSX-файл.
5. Пользователь скачивает результат через браузер.

## Безопасность и ограничения

- Пользователь имеет доступ только к данным своей компании.
- Административные действия ограничиваются ролью пользователя.
- Вложения доступны только пользователям, имеющим доступ к соответствующему сообщению.
- Пароли пользователей не отображаются в интерфейсе при редактировании.
- Конфигурационные секреты должны храниться в переменных окружения.
- Для значимых действий пользователей ведется audit log.
- В журнале действий фиксируются операции, важные для прослеживаемости: создание, изменение, подтверждение, деактивация или удаление объектов, если такие действия предусмотрены логикой системы.
- Snapshot-данные этапов сверки позволяют сохранять состояние этапа и не изменять его задним числом.
- Система реализована как учебный проект и не заявляет полное соответствие промышленным GMP/GxP-процедурам или процессу регламентной валидации.
